TP3 : Contrôle d'accès décentralisé avec smart contracts (RBAC et ABAC)

Objectifs

  • Implémenter un contrôle d'accès décentralisé avec les modèles RBAC (rôles) et ABAC (attributs).
  • Développer une marketplace d'enchères décentralisée (smart contracts, Hardhat).
  • La déployer sur son propre réseau Besu.
  • Programmer et exécuter des scénarios de tests.

Vous développez deux smart contracts :

  • AccessManagement.sol : gère les rôles et les attributs des utilisateurs.
  • BusinessManagement.sol : marketplace d'enchères qui vérifie les permissions en interrogeant AccessManagement.

Spécification

AccessManagement.sol (RBAC + ABAC)

RôleDroits
ROOTEntité qui déploie le contrat. Peut ajouter des administrateurs.
ADMINPeut enregistrer des utilisateurs.
SELLERPeut créer des enchères (sous condition d'attribut).
BUYERPeut enchérir.
FonctionDescription
addAdmin(address admin)Ajoute un administrateur (ROOT uniquement).
addUser(address user, string role, string department)Enregistre un utilisateur avec un rôle (SELLER ou BUYER) et un attribut (département).
delegateRights(address toSeller)Un SELLER délègue ses droits à un autre SELLER.

Contrôle ABAC : l'attribut department (ou tout autre attribut) restreint les permissions ; par exemple, seuls les sellers d'un département donné peuvent vendre certains produits.

Choix de conception à préciser et justifier dans votre README (l'énoncé ne les impose pas) :

  • Que signifie « déléguer ses droits » : transfert ou partage ? Durée ? Le délégué peut-il redéléguer ? Peut-on révoquer ?
  • Comment relier un produit (itemId) à un département autorisé pour appliquer la règle ABAC ?
  • Rôles et départements : string ou type énuméré / bytes32 (coût en gas, risque de fautes de frappe) ?
  • ROOT peut-il aussi enregistrer des utilisateurs ? Peut-on changer le rôle d'un utilisateur ?

BusinessManagement.sol (marketplace)

FonctionCondition
createAuction(uint itemId, uint minPrice)Seuls les SELLERS (respectant la règle ABAC) peuvent créer une enchère.
placeBid(uint auctionId)Seuls les BUYERS peuvent enchérir ; l'offre doit dépasser le minimum et l'offre en cours.

Les vérifications se font en interrogeant AccessManagement via une interface :

// Proposition d'interface, à adapter à votre implémentation
interface IAccessManagement {
    function isSeller(address user) external view returns (bool);
    function isBuyer(address user) external view returns (bool);
    function departmentOf(address user) external view returns (string memory);
    function canSell(address user) external view returns (bool); // rôle SELLER, direct ou délégué
}

Points de sécurité à traiter :

  • Utiliser msg.sender et jamais tx.origin pour l'authentification.
  • Restituer l'ancienne meilleure offre sans risque : privilégier un retrait par l'enchérisseur (pull payment) plutôt qu'un envoi direct, et appliquer le motif checks-effects-interactions (voir le risque de réentrance).
  • Émettre des événements (AdminAdded, UserAdded, RightsDelegated, AuctionCreated, BidPlaced) pour l'audit.

Mise en place

1. Projet Hardhat

mkdir access-dapp && cd access-dapp
npm init -y
npm install --save-dev hardhat@^2 @nomicfoundation/hardhat-toolbox@^5 dotenv
npx hardhat init

2. Contrats

Créez contracts/AccessManagement.sol et contracts/BusinessManagement.sol (le second reçoit l'adresse du premier dans son constructeur).

3. Configuration (hardhat.config.js)

require("dotenv").config();
require("@nomicfoundation/hardhat-toolbox");

module.exports = {
  solidity: {
    version: "0.8.24",
    settings: { evmVersion: "paris" },   // compatibilité avec un genesis Besu sans Shanghai
  },
  networks: {
    hardhat: { chainId: 1337 },
    besu: {
      url: "http://127.0.0.1:8545",
      accounts: process.env.SECRET_KEY ? [process.env.SECRET_KEY] : [],  // clé de TEST, dans .env
    },
  },
};

Fichier .env : SECRET_KEY=0x... (clé d'un compte de test de votre réseau Besu). Ajoutez .env à .gitignore.

4. Déploiement (scripts/deploy.js)

const { ethers } = require("hardhat");

async function main() {
  const access = await ethers.deployContract("AccessManagement");
  await access.waitForDeployment();
  console.log("AccessManagement déployé à :", await access.getAddress());

  const business = await ethers.deployContract("BusinessManagement", [await access.getAddress()]);
  await business.waitForDeployment();
  console.log("BusinessManagement déployé à :", await business.getAddress());
}

main().catch((error) => {
  console.error(error);
  process.exitCode = 1;
});
# Réseau Besu (TP1) :
npx hardhat run scripts/deploy.js --network besu
# Alternative locale :
npx hardhat node

Scénarios de test à couvrir

  • Ajout d'un administrateur, d'un seller et d'un buyer.
  • Refus : un compte non autorisé ajoute un administrateur ou un utilisateur.
  • Délégation de droits seller → seller (et comportement choisi pour la révocation).
  • Refus : création d'enchère sans rôle SELLER, ou par un seller hors du département autorisé.
  • Refus : enchère sans rôle BUYER, offre trop basse.
  • Fonctionnement de bout en bout sur le réseau Besu.
